# Shape a coding request

Use the user's own words with `memory_shape_request` to bring relevant project decisions into the conversation. Look at the screen, example or code they already shared, and use any available, authorized project reads before asking them for facts you can discover. If memory is unavailable, work with what the user already provided.

Find the moment that matters to the user. When two plausible interpretations lead to different outcomes, ask one question they can answer from experience. For “I keep getting lost on this page,” try “Is it harder to find the setting the first time, or to find your place again after changing it?” Tailor the choices to the actual project and accept an answer in their own words. A recent incident or a before/after example can be easier than picking from a list.

Use their answer to describe a small visible improvement and how you would tell it worked. For example, if they lose their place after saving, return them to the setting they just changed and check that it stays in view. Let the host agent choose technical details. If they say “you decide,” pick a reversible starting point and make it concrete. For a request to implement, proceed once the outcome is clear enough. For a discussion, give a proposal or sketch.

Keep the working agreement in this conversation. A trial idea becomes a standing preference only when the user asks for that.
